## Rule

Do not globally ban cross-schema foreign keys and do not automatically permit them. A schema boundary is an ownership boundary within the same database, not a database or authorization boundary. Select enforcement, lifecycle/deletion behavior and reference strategy per relationship, with source/target owners, invariant, scope, nullability, delete/update action, migration plan and test evidence. A foreign key never transfers write authority or grants access.

P05 owner-approves a hybrid relationship strategy: FK where appropriate per edge; selective composite foreign keys where same-parent scope must be proven; hybrid lifecycle and deletion behavior per entity; and typed FK or application reference according to relationship shape. The current edge-policy approvals are scoped: D9–D13 approve X01–X05 respectively, and X06 is separately owner-approved and validated under V03. X01–X05 are implemented in checked-in Prisma/schema-migration source, but D9–D13 do not establish the state of a current database or full validation. Edges X07–X16 remain individually unapproved absent another explicit approval; X06 is the separate approved exception. A composite FK is not a default for every company/plant relation, and an application reference must be identified as such rather than called a database FK.

Recommend a physical FK when a stable, typed relationship must never dangle; both records share database lifecycle; PostgreSQL/Prisma can express and migrate the relationship; delete behavior is explicit; and the target's owner approves its integrity cost. Prefer a composite FK when the invariant includes company/organization/plant consistency and a unique target key exists for the composite. Recommend an application reference plus same-transaction owner validation for polymorphic, external, optional or lifecycle-decoupled references where a typed FK is not safe. Label that reference honestly; it is not a database FK.

## Delete and update handling

Candidate default for durable posted/auditable facts is `RESTRICT`/non-destructive lifecycle rather than cascade deletion. This is not a universal policy: draft cleanup, privacy erasure, historical anonymization and retention need explicit owner/legal decisions. Do not use soft-delete as proof of audit retention or as authorization revocation. Primary keys should be immutable; business-key changes require explicit history/snapshot behavior.
