# V04.4 Tenant Technical-Feasibility Spike Plan

**Type:** Reproducible, isolated technical-feasibility plan; not an execution report.  
**Baseline:** Approved V04.2 design and V04.3 consolidated review; PostgreSQL 17.6, Prisma ORM/Client 7.10.1.  
**Policy:** D1–D15 remain `OWNER_APPROVED` (2026-11-06); no decision or gate state is changed here.  
**Gate:** V04 remains `BLOCKED`; this plan is not implementation, technical-validation evidence, or a V04 PASS.

## 1. Purpose and scope

Define a repeatable spike to check whether the approved tenant-scope structural design can be represented, migrated, and tested with the pinned Prisma/PostgreSQL toolchain. The eventual spike is limited to temporary schema models, generated client output, migration SQL, database constraints, referential actions, wrong-parent rejection, and approved membership/assignment uniqueness semantics where their physical predicates are defined.

The spike does not implement production tenant models, authorization, protected operations, invitations, a permission catalog, RLS, Service Principal entities, or application features. It does not reconcile or rewrite the older P05 matrix/ERD. The later edge-specific D9–D13 approvals in the V04.2 design are the operative decisions for X01–X05.

**Plan-only boundary for this change:** Do not run commands, tests, builds, Prisma operations, containers, database queries, migrations, or experiments while preparing this document. Do not change existing files, source, schema, migrations, tests, CI, dependencies, Docker/Compose, or environment configuration. Only this plan document is in scope.

## 2. Baseline and constraints to preserve

- Use the repository's pinned Node.js 26.x, pnpm 10.20.0, Prisma CLI/Client/`@prisma/adapter-pg` 7.10.1, and PostgreSQL 17.6. Record exact resolved versions and container image identity in future evidence; a manifest pin alone is not compatibility evidence.
- The current schema has validation fixtures and Better Auth persistence models, but no tenant models. Preserve the canonical `core.User.id` scalar type and mapping; do not make it a tenant key or add user-level organization uniqueness.
- D1: `ACTIVE` and `SUSPENDED` occupy the organization slot; `PENDING`, `REVOKED`, and `ENDED` do not. `SUSPENDED` denies access while occupying the slot. A candidate partial-index predicate is `status IN ('ACTIVE','SUSPENDED')`; confirm that the exact SQL predicate implements D1 before using it. Restore `SUSPENDED` on the same membership row; `REVOKED` and `ENDED` are terminal, and a later grant is a new episode. Timestamps are audit/history metadata, not authorization intervals.
- D5: Organization→Company database cardinality is zero-to-many, each Company has one Organization, and there must be no permanent unique constraint on `Company.organizationId`. Initial single-company-first remains a provisioning/UI policy. Company access still requires explicit Company Membership.
- D6: both CompanyMembership and PlantAssignment use the shared status vocabulary `ACTIVE`, `SUSPENDED`, `REVOKED`, `ENDED`. `ACTIVE` and `SUSPENDED` occupy the relevant pair slot; `REVOKED` and `ENDED` release it. `SUSPENDED` denies access but retains the slot and may be restored to `ACTIVE` on the same row. Terminal episodes remain historical; a later grant creates a new episode. Candidate partial unique predicates are `status IN ('ACTIVE','SUSPENDED')`, independently scoped to `(userId, companyId)` and `(userId, plantId)`. Additional roles use separate RoleAssignment records. These are approved policy-derived candidates, not validated DDL.
- X01–X05 must retain D9–D13's exact columns, tuple order, and `ON DELETE RESTRICT` / `ON UPDATE RESTRICT` actions. Add composite target keys only if PostgreSQL requires them for the exact foreign keys.
- D10, D12, and D13 expressly allow Core-owned validation in the same transaction if Prisma/provider cannot safely map the respective composite relations. A fallback is not a database FK and must preserve the same-parent invariant with negative tests.
- D14 applies to role edges only: each Role Assignment matches its typed scope parent and a Role Definition; role edges use `RESTRICT`; role primary keys are immutable; used definitions are retired/disabled rather than hard-deleted; revoked assignments/history are preserved. Do not infer a full role catalog or grant matrix.
- D2 approves invitation handling, not Invitation FK edges. D15 approves the Service Principal policy, not extra P05 edges or a permission catalog. Do not test or claim those edges as approved.
- Keep X06 unchanged. Its existing behavior is `ON DELETE RESTRICT` and `ON UPDATE CASCADE` for both session→user and account→user FKs. Existing migration files and their history must remain intact.

## 3. Isolation design and stop conditions

2. Use a separate ephemeral `postgres:17.6` container with a collision-resistant temporary name, no Compose project, no named volume, and a dynamically assigned host port explicitly bound to `127.0.0.1`. Use the container's disposable writable layer or other explicitly temporary storage; remove the container to destroy it. Use fresh throwaway credentials supplied only through the launching process, never checked into files or printed in evidence.
3. Verify the running image/version, container name, host binding, dynamically assigned port, and disposable storage before connecting. The only permitted database URLs are for uniquely named databases on this container (fresh, upgrade, and, if Prisma requires it, shadow). Never use the repository's `DATABASE_URL`, the existing Compose service, host port `5433`, or the `sap_core_postgres_data` volume.
4. Write a temporary Prisma config in the copied workspace, explicitly pointing to its copied schema and migration directory. Supply `DATABASE_URL` and, if needed for `migrate dev`, `SHADOW_DATABASE_URL` from process-local environment values that target only this container. Never inherit a repository `.env` file. Confirm both URLs resolve to the verified ephemeral server before each database-changing command.
5. If any boundary cannot be proven, stop before Prisma or SQL touches a database. Do not improvise against the existing service. Do not use `prisma migrate reset`, `prisma db push`, or `docker compose down -v` at any stage.

The workspace should capture the source commit, exact commands, tool versions, container identity and port, schema/config copies, migration checksums, and redacted output. Do not include credentials or user data.

## 4. Temporary schema and migration workflow

1. Establish the baseline from the copied current schema and six-migration history. Keep a pristine baseline copy for comparison. Add candidate tenant models/relations only to the workspace copy, reusing the existing `User` model and its ID type. Generate the Prisma Client only into the temporary workspace.
2. Use the workspace-local pinned CLI for `prisma validate` and `prisma generate`. For migration authoring, use Prisma 7.10.1's `migrate dev --create-only` against the isolated development/shadow databases, then inspect the generated migration before applying it. Add any required partial-index SQL only to an experiment migration in the workspace and review it explicitly. Do not edit the copied historical migrations.
3. Review generated Prisma mapping and migration SQL for schema names, columns, nullability, key order, FK target keys, and exact delete/update actions before database application. If a mapping is unsupported, record the Prisma/provider failure and test only the corresponding D10/D12/D13-approved Core same-transaction fallback in a temporary harness. Do not weaken an invariant or describe fallback validation as an FK.
4. **Fresh replay:** create a fresh empty database in the isolated container. Apply the copied six-migration history plus the reviewed experiment-only migrations with the pinned `prisma migrate deploy`. Confirm migration status and inspect actual PostgreSQL catalog state. No existing database is reset.
5. **Upgrade replay:** create a second empty throwaway database. First deploy only the unchanged six-migration history, representing the current V03 baseline; then point the copied workspace at a migration directory containing that same history plus the experiment-only forward migration(s), and deploy those forward migrations. Confirm history, status, and catalog state. Do not fake an upgrade by editing applied migration history.
6. If `migrate dev` requires a shadow database, use a separately named throwaway database on the same isolated server and verify its URL before each use. Shadow operations must never target the fresh/upgrade database or an external server.
7. Record how the experiment database was created and disposed. On completion, stop/remove only the uniquely named temporary container and remove the external workspace. Never run broad cleanup commands that may affect another project or volume.

The command sequence for a future execution is therefore: establish and verify isolation; install from the copied lockfile; validate and generate; author a create-only migration; review SQL; run fresh and upgrade deploys; run the temporary test harness; inspect database metadata; capture evidence; dispose of only the isolated resources. This sequence is a plan, not a claim that any command has run.

## 6. Evidence and decision rules

A future result is **PASS for a specific feasibility case only** when all applicable items are reproducible: exact pinned versions recorded; Prisma validation/client generation succeed; reviewed SQL is applied through the temporary migration history; fresh and upgrade replay both succeed; PostgreSQL catalog metadata matches the approved tuples/actions; positive and negative tests behave as expected; applicable races preserve approved uniqueness/history semantics; X06 is unchanged; and the exact commands/results are retained with secrets redacted.

A Prisma validation, generation, migration, metadata, or behavior mismatch is a **FAIL for that candidate mapping**, not permission to weaken the policy. Use only the expressly approved Core same-transaction fallback for X02/X04/X05 where applicable, with the invariant and negative wrong-parent tests retained. Report unsupported or unresolved cases precisely.

A case depending on unresolved policy remains **BLOCKED / NOT RUN** until that prerequisite is supplied. D6's status vocabulary and candidate predicates are now owner-approved; its physical feasibility and behavior remain **NOT RUN** pending separate execution approval. Missing evidence is never PASS. A successful isolated structural spike does not establish authorization, application tenant isolation, full V04 completion, or production readiness.

Retain a compact evidence bundle in the temporary workspace for review: baseline commit; tool/container versions; redacted connection target details; schema diff; generated client result; reviewed experiment migration SQL; checksums of historical migrations; fresh/upgrade migration logs and status; FK/index catalog output; test cases/results including race outcomes; failures/deviations; cleanup confirmation; and explicit residual risks. Do not copy experiment artifacts into repository migrations or tests as part of this plan.
