# V04.5.1 X06 Implementation and Isolated-Validation Record

## Approved X06 policy

Both Better Auth foreign keys to the canonical user use ON DELETE RESTRICT and ON UPDATE RESTRICT:

- core.session.userId → core.user.id
- core.account.userId → core.user.id

There is no database-level ON DELETE CASCADE for either relationship. Better Auth hard deletion remains disabled. Existing migration history is immutable; any change to these foreign-key actions is made by a forward migration.

## Implementation

The checked-in forward migration is `prisma/migrations/20261107112700_v0451_tenant_scope_schema/migration.sql`. It replaces the existing Session and Account auth-user foreign-key constraints, preserving the constraint names `session_userId_fkey` and `account_userId_fkey`, and sets both actions to ON DELETE RESTRICT ON UPDATE RESTRICT.

The migration is part of the V04.5.1 candidate. This record does not claim that it has been applied to a hosted or production database.

## Migration-history reconciliation

The original migration `20261106010425_phase_0_3_v03_better_auth_identity` created both auth-user foreign keys with ON DELETE CASCADE ON UPDATE CASCADE. The later migration `20261106090000_p05_x06_restrict_auth_user_deletion` changed ON DELETE to RESTRICT while retaining ON UPDATE CASCADE. The V04.5.1 forward migration brings both constraints to ON DELETE RESTRICT ON UPDATE RESTRICT. Neither historical migration was edited.

## Isolated validation record

The seven checked-in migrations were replayed in order into an empty database using PostgreSQL 17.6 in a disposable Docker environment. The full replay succeeded, and Prisma migrate status reported that the database was up to date.

Catalog inspection confirmed that both core.session.userId → core.user.id and core.account.userId → core.user.id use RESTRICT for DELETE and UPDATE. Transactional behavior tests against this full-replay database confirmed:

- Deleting a User referenced by a Session was rejected.
- Updating the ID of a User referenced by a Session was rejected.
- Deleting a User referenced by an Account was rejected.
- Updating the ID of a User referenced by an Account was rejected.

The behavior-test transaction ended with ROLLBACK. A follow-up residual-fixture query returned zero test users, organizations, sessions, and accounts.

## V04.5.1 fresh replay and FK catalog audit — 2026-11-08

Separate from the seven-migration X06 replay above, all nine checked-in migrations were applied successfully in order to a fresh database in a local disposable PostgreSQL environment. `prisma migrate status` reported that the database was up to date.

The catalog audit reported 10 schemas, 18 tables, 19 foreign keys, 55 indexes, and 9 migration records. All 19 foreign keys were validated in the catalog audit:

- `master_data.validation_references.validation_record_id` uses `ON DELETE CASCADE` and `ON UPDATE CASCADE`, consistent with the checked-in Prisma schema and migration.

The 55-index figure is the catalog count; it does not mean every index was individually checked. This was local disposable-database evidence, not inspection of a current, hosted, or production database. It does not establish complete V04 acceptance or change V04 from `BLOCKED`; V05–V10 and Phase 1 remain `BLOCKED`.

## Scope and limitations

The seven-migration X06 replay and this separate nine-migration fresh replay are isolated local PostgreSQL validations. Neither establishes the state of a hosted or production database. No historical migration was changed. Application-level Better Auth lifecycle behavior, overall tenant authorization, protected operations, RLS, and application tenant isolation are not established by these replay and catalog results.
