# V04.1 Tenant Isolation and Authorization Boundary Audit

**Audit type:** Static, audit-only repository review. No implementation or policy changes.  
**Scope:** Organization, company, plant, membership, role, canonical-user, authorization, tenant query, and PostgreSQL RLS boundaries.  
**Gate result:** `V04 BLOCKED`. This document records the design baseline and implementation gaps; it is not V04 pass evidence.

## Executive summary

The approved architecture defines an organization as the initial tenant context, a company as the initial operating/accounting boundary, and a plant as an operational site. Organization membership, company membership, and explicit plant assignment are separate access inputs. A canonical ERP user is not itself a tenant grant. The approved authorization design is server-side, scoped, deny-by-default, and separate from Better Auth authentication. Application authorization is primary; selective PostgreSQL RLS may be added as defense-in-depth after its scope and safe pooled-connection behavior are proven.

Those decisions are architecture approvals, not by themselves evidence that the controls exist. This V04.1 audit's original source inventory is a historical snapshot at HEAD `cd183e4`: the Prisma schema contained Organization, Company, Plant, OrganizationMembership, CompanyMembership and PlantAssignment models with the D9–D13 X01–X05 relations, and migration 7 contained the corresponding FK DDL. A later V04.5.1 record dated 2026-11-08 documents a successful fresh replay of all nine checked-in migrations in a local disposable PostgreSQL environment, with Prisma reporting the database up to date. Its catalog audit recorded 10 schemas, 18 tables, 19 foreign keys, 55 indexes and 9 migration records, with all 19 foreign keys validated. This later evidence supersedes the earlier statement that a nine-migration fresh replay was not established; it does not establish a hosted/production database state, a staged-upgrade replay of all nine migrations, complete edge-level behavior, or tenant authorization. The original audit itself did not query a database.

The implemented structural relationships do not constitute an end-to-end tenant boundary. The inspected application still lacks a demonstrated protected tenant business operation and complete tenant authorization/data-access path. A URL, session hint, foreign key, UI check, or proposed RLS policy cannot be credited as authorization. V04 remains `BLOCKED`; V05–V10 remain unchanged and `BLOCKED`; Phase 1 remains `BLOCKED`. No RLS policy is proposed or claimed to exist in this audit.

## Isolation invariants required by the approved model

These are the boundary conditions V04 must eventually demonstrate. They are not claims that a table, policy, middleware, or test currently enforces them.

1. **Authentication is not authorization.** Resolve the principal from a server-verified, currently valid session; then independently validate account state, current membership, scope, action, target, and owner rules.
2. **Canonical identity is global identity, not a tenant grant.** Do not encode the initial one-organization operating policy as a permanent global uniqueness constraint on the canonical user. Membership and reassignment/history belong to relationship policy.
3. **Organization scope is explicit.** Under the approved initial policy, an ERP user belongs to one organization. Any future change to that product policy must be explicit; it must not be inferred from a user ID, email, or session record.
4. **Company scope is explicit and parent-consistent.** A company belongs to the selected organization. Organization membership alone does not authorize every company or company resource; company membership and scoped permissions are checked independently.
5. **Plant scope is explicit and parent-consistent.** A plant belongs to the selected company, and a plant-scoped operation requires an active plant assignment. Company membership does not imply access to every plant.
6. **Selectors are untrusted.** Organization/company/plant IDs from a route, form, client state, or session hint can select a requested context only. Resolve and validate them against current server-side records for the authenticated principal on every protected operation.
7. **Target ownership and action are both checked.** Check that the specific target belongs to the authorized scope and that the action is allowed for that principal/role/resource lifecycle. A guessed or foreign primary key must not widen scope or disclose resource existence.
8. **Deny-by-default and scoped precedence.** No matching active grant means deny. Permission inheritance is explicit; within the applicable scope, an explicit deny overrides an allow. Platform Admin is not Tenant Admin, and neither role is an implicit grant to bypass tenant boundaries.
9. **All data paths preserve scope.** Apply authorized organization/company/plant predicates in database reads and writes before data leaves the trusted boundary; include list, search, count, export, bulk, report, and mutation paths. Never fetch broad data and filter only after serialization.
10. **Current entitlement governs.** Revocation, suspension, reassignment, account disablement, role changes, and scope changes must affect protected operations under the approved, tested freshness/propagation semantics. A stale session or cache cannot preserve revoked access.
11. **Relationships do not grant authority.** A FK, composite FK, existence check, UI visibility, or foreign-key-valid parent chain is not proof of active membership or permission. Enforce active entitlement in the owning transaction.
12. **Caches and derived data are partitioned.** Cache keys and projections that can expose tenant data must include the principal and authorized scope as appropriate, and be invalidated/recomputed for membership, role, session, or scope changes.
13. **Non-human access is attributable and bounded.** Background and integration work uses dedicated service identities and explicit allowed scopes/actions, not implicit human impersonation or ambient unrestricted database access. Break-glass is separately authorized, time-bounded, attributable, and audited.
14. **Any database defense fails closed.** If RLS is selected, missing, malformed, stale, or mismatched transaction context must not expose rows. Context and policy must be applied on every relevant connection/path and be safe under commit, rollback, cancellation, and pool reuse.

## RLS feasibility and V07 dependency

**Current posture:** RLS is not enabled or evidenced in the inspected migrations. P08 makes application authorization primary and RLS selective defense-in-depth. No policy should be inferred from the approved architecture or added by this audit. Application-level scope resolution and database predicates are required even if no RLS policy is ultimately selected.

**Feasibility conditions before any selected policy can count as a control:**

1. Identify the exact tenant-scoped tables and row predicates only after P07 ownership/scope and the P05 relationship decisions for those edges are settled. Decide explicitly whether the policy is organization-, company-, plant-, or mixed-scope; do not invent a universal `tenant_id` rule.
2. Establish a trusted server-side context from the authenticated principal and current memberships/assignments. Client-supplied context must not be written directly to a database setting or treated as authority.
3. Install context transaction-locally on the same physical connection and within the same transaction as protected queries (for PostgreSQL, a transaction-local mechanism such as `SET LOCAL` or `set_config(..., true)` is a candidate, not a selected implementation). Session-level `SET` is unsafe as tenant state in a pooled connection.
4. Prove that an unset, empty, malformed, stale, or cross-scope context denies access. Verify both reads and writes, and ensure all protected queries use the context-bearing transaction rather than an unrelated client/connection.
5. Test context isolation across commit, rollback, thrown errors, timeout/cancellation, connection reuse, concurrent requests, and pool checkout/check-in. The next borrower must not inherit prior tenant state; the caller must not continue if context setup failed.
6. Define actual runtime, migration, read-only, job, and administrative PostgreSQL role attributes and grants. Test as the runtime role, not only as a superuser or migration/table owner. PostgreSQL table owners ordinarily bypass RLS unless row security is forced; superusers and roles with `BYPASSRLS` bypass it. The chosen privileges and any `FORCE ROW LEVEL SECURITY` behavior must be demonstrated on the pinned deployment/provider. No such role configuration is currently evidenced.
7. Keep application authorization in place. RLS cannot decide business action grants, explicit deny precedence, separation of duties, service identity attribution, record lifecycle, or safe response shaping by itself.

**V07 is a prerequisite, not a substitute for V04.** The execution register keeps V07 `BLOCKED` for pooled connection reuse, transaction-local context isolation, cleanup, and failure tests. Until that behavior is established with the actual Prisma/adapter/provider transaction path, RLS based on mutable connection context is not a safe demonstrated defense. Passing V07 would prove the selected pool/context mechanics only; V04 would still need correct scope resolution, policies if selected, application predicates, privilege review, and adversarial authorization tests. V06 transaction/concurrency behavior and P09/G10 provider/role details are related dependencies and must be accounted for where they affect the selected path.
