## 3. Preflight findings

A read-only schema inspection on both targets returned identical structure:

- `core.organization`: `id uuid NOT NULL`, `created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP`, `updated_at timestamptz NOT NULL`.
- `core.company`: `id uuid NOT NULL`, `organizationId uuid NOT NULL`, `created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP`, `updated_at timestamptz NOT NULL`.
- FK `company_organizationId_fkey`: `FOREIGN KEY ("organizationId") REFERENCES core.organization(id) ON UPDATE RESTRICT ON DELETE RESTRICT`.
- Primary keys exist on both tables.

The D5 fixture inserts therefore supplied `updated_at` explicitly. The first attempted D5 script did not execute successfully because it connected using the nonexistent `postgres` role in these custom-superuser containers. This was an authentication/role-selection error, not a database or migration failure. The corrected run used the verified per-container roles and completed.

## 4. D5 execution and assertions

Each target was tested independently with fresh UUID fixtures inside one explicit transaction. The test transaction was rolled back; subsequent queries checked that no Organization or Company fixture remained.

| Assertion | Fresh | Staged |
|---|---|---|
| An Organization can exist with zero Companies | PASS | PASS |
| One Organization can have two Companies | PASS | PASS |
| A Company referencing a nonexistent Organization is rejected by `company_organizationId_fkey` | PASS | PASS |
| No valid single-column unique index exists on `core.company("organizationId")` | PASS | PASS |
| Organization fixture absent after rollback | PASS | PASS |
| All Company fixtures absent after rollback | PASS | PASS |

The index listing on both targets was identical:

- `company_organizationId_idx`: ordinary B-tree index on `organizationId`.
- `company_organization_id_id_key`: unique composite B-tree index on `(organizationId, id)`.
- `company_pkey`: primary key on `id`.

This supports the approved zero-to-many database cardinality: one Organization can have zero or multiple Companies, while each Company must reference one existing Organization. The composite unique index does not impose uniqueness on `organizationId` alone.
